# OXESpace 0.15.0

This release refines the Code and Thread workspaces around a shared desktop design and clearer session management.

## Thread

- Project and conversation navigation now has a clearer hierarchy. Each project opens new conversations from its own plus action; conversation menus expose side-by-side opening, rename, pin, read/unread, archive, restore and delete.
- The reading area is wider and has its own persistent text-size control. Long histories keep rows in order, remain scrollable, and reopen at the previous reading position or at the latest message.
- Requests for command approval show readable details. Assistant replies can be copied, and project changes can open Markdown files in a large rendered reader.
- Conversation and provider-session IDs are distinguished so the ID needed for native resume is easy to find.

## Code and shared desktop

- The Workbench palette is the default for new workspaces and is adopted once by older workspaces; subsequent theme choices remain user-controlled. New terminal defaults use Cascadia Mono at 16 px.
- Terminal details show runtime information first and offer a searchable list of native Codex and Claude sessions in the workspace directory. The session ID or exact CLI resume command can be copied.
- Workspace tools use a shared side area, preserving terminal state while changing tools or moving between Code and Thread. Settings navigation and dialogs have been refined for narrower windows.
- An update indicator appears in the app header when a newer release is available. Development builds and Linux package installs link to the release for manual updating.

## Validation

The current checkout passed type checking, lint with no errors, the production build and bundle budgets, 1,059 Electron tests, 20 standard Playwright scenarios, and 15 performance-gate scenarios on Windows. Two data-dependent visual audits are excluded from the standard Playwright run; an isolated copy of a long local conversation passed the bottom-stability audit with zero measured drift. Windows and Linux packaging and packaged smoke tests are part of the release workflow.

The local UI tests simulate provider responses. Live provider authentication and responses remain outside that fixture-based validation.
