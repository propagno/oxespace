# CCR A67 (1.5.0, Fase 10): the workspace colour reaches the phone

- **Owner:** MOBILE (oxespace-29). BACKEND reviews the desktop part.
- **Acceptance:** A67 (N11): the workspace colour reaches the phone through an additive C5 field (`android:generate`),
  and an APK without the field keeps working. Evidence: protocol and JVM tests.
- **Status:** draft. BACKEND reviews the desktop part, and HML the field question (M10), before the OXE execute.
- **Used by:** CCR phone-screens (#688), T-P1.6 the workspace chip.

## What's on main today

- **Stored:** `workspaces.color INTEGER NULL`, between 1 and 8 (`093_workspace_color.sql`). Null means "not chosen".
- **Shown:** `shared/workspace-color.ts` `workspaceColorIndex(ws)`. It returns the chosen slot, or an FNV-1a hash of the
  id (1–8) when none was chosen. The desktop renderer always shows that resolved slot.
- **C5:**
  - `RemoteWorkspace { id, name, active, panes }` has no colour;
  - `RemoteWorkspaceRow` (`electron/main/services/remote/desktop.ts`) doesn't select `color`;
  - `toWorkspace` (`filters.ts`) doesn't map it.
- **The phone:** `OxeTokens.kt` already has `ws1…ws8` and `ws1Fg…ws8Fg`. Every shipped APK decodes with
  `ignoreUnknownKeys = true` (`RemoteFrames.kt`; the same on tag v1.4.3), so an added field is ignored.

## Decision: send the resolved slot, not the stored one

The desktop sends `workspaceColorIndex(row)`, so a workspace with no chosen colour still has its derived one. The phone
then shows the same colour as the desktop without porting the hash, and a later change to the hash stays on one side.
The phone never learns whether the colour was chosen or derived; it doesn't need to.

## Protocol (additive, `shared/remote/protocol.ts`)

```ts
export interface RemoteWorkspace {
  id: string; name: string; active: boolean; panes: RemotePane[]
  /** 1.5.0 A67: the colour slot the desktop shows (1–8), chosen or derived (shared/workspace-color.ts). Absent from an
   *  older desktop. */
  color?: number
}
```

- **Not a new enum:** it's a number, so `android:generate` adds `val color: Int? = null` to `RemoteWorkspace`.
- **No `schemaVersion` bump:** the field is additive.

## Tasks and their exact files

### T-A67.1 The desktop sends the colour (BACKEND reviews)

- `electron/main/services/remote/desktop.ts`:
  - `RemoteWorkspaceRow` gains `color: number | null`;
  - the `workspaces()` query selects `color`.
- `electron/main/services/remote/filters.ts`: `toWorkspace` adds
  `color: workspaceColorIndex({ id: row.id, color: row.color })`. Only `id` and `color` go into the call, no other
  workspace field, so the mapper's "names what it keeps" rule still holds.
- `shared/remote/protocol.ts`: the field above.
- `mobile/android/protocol/src/main/kotlin/com/oxespace/mobile/protocol/RemoteProtocol.kt`: generated by
  `npm run android:generate`, never by hand.
- **No change to the topic:** `workspaces` is a polled `ListTopic`, so a colour change on the desktop reaches the
  subscribed phone as an event, like a rename.

### T-A67.2 The phone reads it

- `mobile/android/app/src/main/java/com/oxespace/mobile/ui/components/WorkspaceChip.kt` (#688 T-P1.6):
  - `color` in 1–8 → `wsN` / `wsNFg`;
  - absent, or out of range → the neutral chip.
- No change in the protocol module beyond the generated class.

## Field question (M10, HML)

- **On the stand-in phone (R143), against a real gateway:**
  - the workspaces list shows each workspace's colour equal to the desktop's;
  - changing a colour on the desktop changes it on the stand-in within one poll;
  - resetting a colour to "not chosen" shows the **derived** slot (`workspaceColorIndex`) within one poll, not
    neutral. That's where a drift between the two sides would show;
  - a colour change neither reorders nor rescrolls the list: the same ids, in the same order, before and after the
    event.
- **Colour is never the only signal:** the chip always shows the workspace name. `ComponentsSnapshotTest` asserts the
  name is present on every chip, in light and dark.
- **An older APK:** the v1.4.3 stand-in subscribes to this desktop and lists the workspaces as before.
- **An older desktop (optional):** the new APK against a 1.4.3 desktop on the stand-in shows neutral chips and no
  error. JVM case 2 covers the decode; this covers the screen.
- **Busy case:** none. The field is one integer per workspace and adds no traffic.

## Out of scope

- Choosing a colour from the phone. The phone stays read-only for workspace settings.
- Colours on rows other than workspaces, such as threads or agents. That needs a `workspaceId` on the agents row
  (MG1, 1.5.x).
