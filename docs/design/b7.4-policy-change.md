# B7.4 · A policy change made outside OXESpace waits for the person

> Screen spec for the `policyChange` request, the narrowing notice and the `policy.change.pending` refusal.
> Slice S1 · Owners: BACKEND (store, watcher, request, codes) and FRONTEND (modal variant, Settings states).
> Acceptance: #357 (cases 1–10). Copy gate: [glossary](glossary.md). Built on the B10 contract
> (`shared/types/approvals.ts`) and the F18 modal (#243).

## 1. What the person must understand

Something on disk changed what agents are allowed to do in this project, and OXESpace didn't make that change. Until
the person decides, the rules they accepted stay in force. Deny keeps those rules, and the file is never rewritten
silently.

Who made the change can't be known. A file is a file: the editor, `git checkout`, an agent's shell and a script all
look the same. **The request never names an agent as the author.** The requester is the app (`kind: 'app'`, label
"OXESpace"), and the text says "outside OXESpace".

## 2. When each thing happens

| Change on disk (`.oxespace/policy.json`, or the security part of `oxe.yaml`: `thread.tools` / `toolModes` / B7.3 rules) | What the person sees | #357 |
|---|---|---|
| Widens: removes a deny rule, adds an allow rule, or raises a tool group (off → on demand → always) | **Request** (§3) | 1, 2, 3 |
| File deleted | **Request**, variant `deleted` | 7 |
| File invalid, or larger than the size limit | **Request**, variant `invalid` / `tooLarge`, **Deny only** | 7 |
| A worktree of the project has a wider file | **Request**, variant `worktree` | 8 |
| Narrows only (stricter, nothing wider) | Applies at once and shows the **narrowing notice** (§4); nothing is asked | 4 |
| Mixed (some rules stricter, some wider) | **Request**: the stricter rules apply at once, the wider ones wait. The diff marks both (§3.3) | — |
| Written by the app (Settings › Tools, Settings › Policy) | Applies; nothing is asked or announced | 5 |
| The same content written again after Deny | Nothing new. The Settings › Policy card keeps its "not in force" state (§5.1) | 6 |
| Settings change while a request is pending | **Refused** with `policy.change.pending` (§5.2) | 10 |

One pending request per file. If the file changes again while its request is waiting, main re-issues **the same
request** with a new `generation` and the new diff, and the modal updates in place. It doesn't stack a second
request. An answer to the old generation is refused as `staleGeneration`, whose existing copy already says "Answer
the current one".

## 3. The request (B10 kind `policyChange`)

### 3.1 Fields

| Field | Value |
|---|---|
| `kind` | `policyChange` (new in `APPROVAL_KINDS`) |
| `requester` | `{ kind: 'app', id: 'oxespace', label: approvals.requester.app }`: "OXESpace" |
| `risk` | `high`. `critical` when the change leaves the project with no deny rules at all (file deleted or emptied, or `allow *`), or turns a group that touches data or secrets (`data`, `db`, `secrets`) to always on. Main computes it; never the file. |
| `title` | `approvals.title.policyChange` |
| `summary` | `approvals.summary.policyChange.<variant>` (§3.2) |
| `target` | The file's path relative to the project, from the app's records: `.oxespace/policy.json`, `oxe.yaml`, or `../<worktree>/.oxespace/policy.json` for the worktree variant |
| `appNotes` | The rule diff, one C3 message per change, wider changes first (§3.3), then `approvals.note.policy.stillAccepted` |
| `agentText` | The file's new text, bounded and untrusted as always (it is the file's text, not the app's), shown in the F18 monospace block. For `deleted` it is empty, and for `tooLarge` it is the first `APPROVAL_AGENT_TEXT_MAX` characters, `truncated: true` |
| `options` | `deny` (**Deny**, the default) and `allowPolicy` (**Allow the new rules**). Only `deny` for `invalid` / `tooLarge`, and for any truncated text, per B10 |
| `defaultOptionId` | `deny` |
| `allowDelayMs` / `enterDisabled` | As B10: 2 s and Enter disabled at `critical`; at `high`, Enter answers Deny (the default) |
| `expiresAt` | B10's 5 min. On expiry the request is denied: same outcome as Deny, history `by: 'timeout'` |

There is no "for this session" answer: a policy is accepted or not. There is also no "Open file" option; the target
path is shown, and the person can open it from the F33 "Open in…" menu once the request is answered.

### 3.2 Copy: title, summary, options

Keys are under `main:approvals.*`. `{{file}}` is the `target` in code style.

| Key | en | pt-BR |
|---|---|---|
| `title.policyChange` | The project's rules changed outside OXESpace | As regras do projeto mudaram fora do OXESpace |
| `summary.policyChange.widened` | {{file}} now allows more than the rules you accepted. Until you decide, the accepted rules stay in force. | {{file}} agora permite mais do que as regras que você aceitou. Até você decidir, as regras aceitas continuam valendo. |
| `summary.policyChange.deleted` | {{file}} was deleted. Allowing it removes this file's rules. Until you decide, the accepted rules stay in force. | {{file}} foi excluído. Permitir remove as regras deste arquivo. Até você decidir, as regras aceitas continuam valendo. |
| `summary.policyChange.invalid` | {{file}} has an error, so it can't be applied. The accepted rules stay in force. | {{file}} tem um erro, então não pode ser aplicado. As regras aceitas continuam valendo. |
| `summary.policyChange.tooLarge` | {{file}} is larger than {{max}}, so it can't be applied. The accepted rules stay in force. | {{file}} passa de {{max}}, então não pode ser aplicado. As regras aceitas continuam valendo. |
| `summary.policyChange.worktree` | The worktree {{worktree}} has its own {{file}}, which allows more than the rules you accepted for this project. Until you decide, the accepted rules apply there too. | A worktree {{worktree}} tem o próprio {{file}}, que permite mais do que as regras que você aceitou para este projeto. Até você decidir, as regras aceitas valem lá também. |
| `option.deny` (exists) | Deny | Negar |
| `option.allowPolicy` | Allow the new rules | Permitir as novas regras |

The F18 block label for `agentText` in this kind is `approvals.textLabel.policyChange`: "The file as it is now" /
"O arquivo como está agora". For `deleted`, the block is replaced by `approvals.note.policy.noText`: "The file no
longer exists." / "O arquivo não existe mais."

For `invalid`, `{{problem}}` is the parser's own short reason, reused from Settings › Policy's `notApplied`. It goes in
one extra note, `approvals.note.policy.problem`: "Error: {{problem}}" / "Erro: {{problem}}".

### 3.3 The rule diff, in the app's own text

The diff is the app's reading of the rules, not a text diff. Main parses the accepted version and the new one, and
emits one note per changed rule. They render as a list in the F18 notes area, each line with a leading sign that is
also read aloud (the sign is in the text, not only in colour):

| Key | en | pt-BR | Style |
|---|---|---|---|
| `note.policy.denyRemoved` | − No longer denied: {{rule}} | − Deixa de ser negado: {{rule}} | wider: `danger` text token |
| `note.policy.allowAdded` | + Now allowed: {{rule}} | + Passa a ser permitido: {{rule}} | wider: `danger` |
| `note.policy.groupRaised` | ↑ {{group}} tools: {{from}} → {{to}} | ↑ Ferramentas de {{group}}: {{from}} → {{to}} | wider: `danger` |
| `note.policy.denyAdded` | + Now denied: {{rule}} (applies already) | + Passa a ser negado: {{rule}} (já vale) | stricter: `muted` |
| `note.policy.groupLowered` | ↓ {{group}} tools: {{from}} → {{to}} (applies already) | ↓ Ferramentas de {{group}}: {{from}} → {{to}} (já vale) | stricter: `muted` |
| `note.policy.more` | and {{count}} more changes in the file below | e mais {{count}} alterações no arquivo abaixo | `muted` |
| `note.policy.stillAccepted` | Deny keeps the rules you accepted. OXESpace doesn't change the file. | Negar mantém as regras que você aceitou. O OXESpace não altera o arquivo. | `muted` |

- `{{rule}}` is the rule in the app's words (layer kind + pattern, e.g. `tool mcp__oxespace__oxespace_db_*`), in code
  style. `{{group}}` and `{{from}}`/`{{to}}` use the Settings › Tools names (off / on demand / always on), not the YAML
  values.
- At most **8** lines, wider ones first; the rest is folded into `note.policy.more`.
- The `danger` style is text colour + sign, never a filled block, so forced colours keep it (the sign carries it).

### 3.4 Layout (F18 modal, this kind)

```
┌ The project's rules changed outside OXESpace ────────── [High] ┐
│ OXESpace                                       .oxespace/policy.json
│ .oxespace/policy.json now allows more than the rules you
│ accepted. Until you decide, the accepted rules stay in force.
│
│  − No longer denied: tool oxespace_db_execute
│  ↑ Data tools: on demand → always on
│  + Now denied: tool oxespace_container_action (applies already)
│  Deny keeps the rules you accepted. OXESpace doesn't change the file.
│
│  The file as it is now  ─────────────────────────── (untrusted)
│  │ { "rules": [ … ] }                                  (scrolls)
│
│                        [ Allow the new rules ]   [■ Deny ]  ← focus
└──────────────────────────────────────────────────────────────────┘
```

- Initial focus is on **Deny**, the default, as in every B10 request.
- At `critical`, **Allow the new rules** shows F18's 2 s hold, and Enter does nothing.
- After the answer, the modal closes and a status line (`role="status"`, the F18 resolution toast) says:
  - Deny: `policy.result.kept`: "The accepted rules stay in force." / "As regras aceitas continuam valendo."
  - Allow: `policy.result.applied`: "The new rules are in force." / "As novas regras estão valendo."
  - Expired: the existing `approvals.expired`.

## 4. The narrowing notice

A stricter-only change applies at once, and the person is told (#357 case 4). The notice is informative and needs no
action:

- A **toast**, `role="status"` (polite), auto-hides after the standard toast time. It is also an F30 activity entry
  ("what's new"), so it can be found later.
- `main:policy.narrowed`: "The project's rules got stricter: {{file}} changed outside OXESpace, and the new rules
  apply now." / "As regras do projeto ficaram mais rígidas: {{file}} mudou fora do OXESpace, e as novas regras já
  valem."
- Action: **View rules** / **Ver regras**, which opens Settings › Policy at that layer.
- Several narrowings within 10 s fold into one toast (the last file wins in `{{file}}`).

## 5. Settings

### 5.1 Settings › Policy: the layer card while a change is pending or denied

The project layer card (`settings:policy.layers.project`) gains one state line above its rules, using the existing
`Notice` primitive (`src/ui/Display.tsx`, intent `warning`):

| State | en | pt-BR | Action |
|---|---|---|---|
| Pending | A change to {{file}} is waiting for your answer. The rules below are the accepted ones and stay in force. | Uma alteração em {{file}} está esperando sua resposta. As regras abaixo são as aceitas e continuam valendo. | **Review the change** / **Revisar a alteração**: focuses the pending request |
| Denied (the file still differs) | {{file}} differs from the rules you accepted, so it isn't in force. The rules below apply. | {{file}} é diferente das regras que você aceitou, então não está valendo. As regras abaixo valem. | **Review the change**: raises the request again (the person's own action, so it's allowed) |

Keys: `settings:policy.change.pending` and `settings:policy.change.notInForce`.

- The rules listed in the card are always the **accepted** ones (what is in force), never the file's.
- **Reload policy** (existing) doesn't accept a change: it re-reads the file, and if it still differs, the state
  stays the same.

### 5.2 The `policy.change.pending` refusal (Settings › Tools and every app write to the gated files)

While a `policyChange` request is pending for a project, main refuses any app write to that project's gated files
(`setToolGroupMode` and the Settings › Policy writes) with the C3 code `policy.change.pending`. This keeps the click
from saving over the agent's file, and keeps the agent's modes from being taken as the project's (#357 case 10).

- `main:policy.change.pending`: "A change to this project's rules is waiting for your answer. Answer it first, then
  change this setting." / "Uma alteração nas regras deste projeto está esperando sua resposta. Responda antes de mudar
  esta configuração."
- Where: inline, under the control that was changed, as the existing Settings › Tools error line (same place as
  `toolGroups.invalidYaml`). It is announced (`role="alert"`, as those errors are).
- The control goes back to the accepted value at once. It never shows the clicked value as saved.
- The line carries **Review the change**, which focuses the pending request.
- The controls stay enabled, so a person who didn't see the request learns why from the refusal.

## 6. History, journal, phone

- `approvals.history()` keeps the decision with `kind: 'policyChange'`, title and summary as above, and `textSha256`
  of the file's text.
- The journal gets a policy-area incident per request (`diagnostics.incidents()`). The code name belongs to BACKEND;
  its text follows `policy.narrowed` / `title.policyChange`.
- The phone can't answer it: a `policyChange` is computer-only, as are guarded requests and permissions. On the phone
  it shows with the existing computer-only reason (mobile-audit-1.4 P2), never with Allow.

## 7. Accessibility

- Modal: F18's dialog semantics. The title is the accessible name, and the summary is the description.
- The diff is a list (`ul`), and each line's sign is part of its text.
- The "(applies already)" suffix says in words what the muted style shows.
- The refusal line uses `role="alert"`; the pending line is a `Notice`. Every action is keyboard reachable,
  with 24 px targets.

## 8. Acceptance (design)

1. Cases 1–3 and 7 of #357 show this modal with the right variant, Deny focused, and the diff lines above. No agent
   is named as the author.
2. A mixed change shows the stricter lines as "(applies already)", and they really are in force while the request is
   pending.
3. Case 4 shows the narrowing toast once, with **View rules**.
4. Case 10 shows the refusal under the control, and the control returns to the accepted value.
5. pt-BR and en use the keys in this spec, and no string is concatenated in the renderer.
6. Forced colours: each diff line's meaning survives through its sign.

## 9. Open to owners (names only, no decisions)

- BACKEND may rename the option id `allowPolicy`, the incident code and the `<variant>` keys. The copy stays as
  written.
- The size limit for `tooLarge` is BACKEND's (`{{max}}` is formatted, e.g. "1 MB").
