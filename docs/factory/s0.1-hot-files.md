## 3. Target layout per hot file

**`shared/messages.ts` (C3 codes) — done in part 1.** `shared/messages/<domain>.ts` declares
`<Domain>MessageParams` and `<DOMAIN>_MESSAGE_CODES`; `shared/messages.ts` keeps every export (`MessageParams`,
`MessageCode`, `MESSAGE_CODES`, `MainMessage`, `isMessageCode`, `isMainMessage`, `mainMessage`, `messageKey`,
`messageValues`) and only merges the domains. A compile-time check fails when a domain declares a code it does not
list. Imports do not change.

**`shared/locales/<lang>/main.json` (C3 words) — part 2.** `shared/locales/<lang>/main/<domain>.json` holds that
domain's `messages.<prefix>.*` subtree; `crash` and `dialogs` stay in `main.json`. A single loader
(`shared/locales/main-catalog.ts`) deep-merges them, refusing a key defined twice. Its consumers are few:
`electron/main/i18n.ts` and `electron/main/agent-text.ts` (read from disk), the `copy-main-locales` plugin in
`electron.vite.config.ts` (copies the merged file to `out/main/locales`), `src/i18n/locales/{en,pt-BR}.ts` (only
`messages`), `src/i18n/i18next.d.ts` (type of `main`), `tests/ui-copy.test.ts` and `tests/messages-contract.test.ts`.
The format of the catalogs does not change (out of scope by the spec), only where the subtree lives.
**Decision needed:** the contract test imports `shared/locales/<lang>/main.json` directly. Either (A) that import
line becomes the loader, with every assertion unchanged; or (B) `main.json` stays as a generated, committed merge with a
test that it equals the fragments. (B) keeps the contract test byte-identical but leaves a generated hot file that
conflicts (resolved by regenerating). Recommendation: (A), reviewed as a one-line contract-test change.

**`tests/messages-contract.test.ts` — part 2b.** It is the hottest file because its `PARAMETERS` table repeats every
code. Target: each `shared/messages/<domain>.ts` also exports `<DOMAIN>_MESSAGE_PARAMETERS` (the names the catalog must
interpolate) and the test merges them; its assertions stay the same. This changes a C3 contract test, so it needs the
Architect's review and the coordinator's OK; until then it remains the one file every new code still touches.

**`shared/locales/<lang>/common.json` — part 3.** Same as main: `shared/locales/<lang>/common/<area>.json` merged by
`src/i18n/locales/<lang>.ts` into the same `common` namespace, so `t('nav.settings')` keeps its key and type. Moving
keys into new i18next namespaces would rename `t()` call sites, so no namespace is added here.

**`electron/main/e2e/mock-ipc.ts` — part 4.** Already partly split (`*-mock.ts` beside it). Target:
`electron/main/e2e/mocks/<domain>.mock.ts`, each exporting `register(context)`; `mock-ipc.ts` loads them with
`import.meta.glob('./mocks/*.mock.ts', { eager: true })`, so a new domain mock touches no shared file. The shared
in-memory state (workspaces, panes) moves to `mocks/context.ts`. Key-set test: register against a fake `ipcMain` and
compare every channel registered with a fixture from origin/main. It stays a separate chunk (not in the production main
bundle), checked by `verify:bundle`.

**`shared/types/ipc.ts` + `electron/preload/api.ts` — part 5.** Finish what `shared/types/ipc/{terminal,semantic}.ts`
started: `shared/types/ipc/<domain>.ts` holds that domain's channel group (`export const THREAD_CHANNELS = {...} as
const`) and its `*Api` interface; `ipc.ts` keeps `IPC_CHANNELS = { thread: THREAD_CHANNELS, ... }` and every
re-export. `api.ts` splits the same way into `electron/preload/api/<domain>.ts`. Key-set test: every
`IPC_CHANNELS` path → channel string, equal to the origin/main fixture (C1 contract tests unchanged). If
`shared/remote/protocol.ts` is ever touched, `npm run android:generate` and commit the Kotlin.

**`src/App.tsx` — part 6.** `src/app/` gets `AppShell.tsx` (top bar, mode switch, overlays), `routes.tsx` (one
entry per mode), `lazy.ts` (the 20+ `lazy()` imports) and `useAppCommands.ts`; `App.tsx` becomes the composition. The
renderer entry keeps at least 8% headroom (`npm run build`, `verify:bundle`) and lazy chunks stay lazy (#302 is
tuning them now). This one is FRONTEND's to execute.

## 5. How in-flight PRs keep merging

- Nothing is renamed, so no PR's code changes meaning; only where a declaration lives moves.
- After a split merges, an open PR that touched the old file resolves its conflict by taking main's version of the
  barrel and putting its own additions in the domain file. For step 1: take `shared/messages.ts` from main, then move
  each `'prefix.x': {...}` line and its `MESSAGE_CODES` entry into `shared/messages/<domain>.ts`. A PR with a new
  prefix (`ipc.*` in #261, `delegation.*` in #196) adds it to the closest domain (`diagnostics`, `agents`), or creates
  `shared/messages/<domain>.ts` and adds one import and one spread to `shared/messages.ts`. The compile-time check and
  `tests/hot-file-keys.test.ts` tell the PR when a code is declared but not listed, or listed nowhere.
- The key-set tests are one-way: every key from before the split must still be there with the same shape; new keys are
  additions. That way the fixtures never become a new hot file.
- One split at a time, never two hot files in the same PR, each after a completed green main run.

## 6. Part 1: `shared/messages.ts`

Why this one first: it is in the top 2 for churn (34 non-merge commits, the same as `main.json`), and the cheapest to
move safely. It is type declarations plus one const array; nothing imports anything but the barrel; the C3 contract test
and every catalog stay untouched. The JSON catalogs need a decision on the contract test (section 3), and the mock and
IPC splits wait on 12-14 open PRs.

What it did:
- 13 files under `shared/messages/` (211 codes: approvals 70, diagnostics 28, thread 28, oxequery 20, oxepost 16,
  mcp 12, activity 7, agents 7, app 6, git 6, workspace 6, remote 4, oxepod 1), each with its doc comments.
- `shared/messages.ts` from 558 to 84 lines: the same exports, the merge, and a compile-time check that every declared
  code is listed.
- `MESSAGE_CODES` keeps its members; only their order follows the domains (nothing depends on the order: lookups use
  a `Set`, and the contract test sorts).
- `scripts/hot-file-keys.mjs messages <file>` prints every code with each parameter's name, optionality and type, read
  by the TypeScript checker. `tests/fixtures/hot-files/message-codes.before.json` is its output on
  `git show origin/main:shared/messages.ts`; on the split files the output is byte-identical (211 codes, 70
  parameters).
- `tests/hot-file-keys.test.ts`: every code from before, with the same parameters; runtime `MESSAGE_CODES` equal to the
  declared codes, each once; no code declared in the barrel; every domain file merged.
