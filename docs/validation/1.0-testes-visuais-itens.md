# 1.0 items from the visual-regression and quality front

For each item added for the release: what it stores, its known limits, what happens if the user goes
back to the previous version, and the test that backs it. "Proved" means a test ran and passed on the
date shown; "not proved" says what is missing. Nothing here has been run against the packaged build
yet: that is the CI job `packaged_smoke_only`, which now includes `e2e/maturity-flows.ts`.

Evidence date: 2026-10-15. Platform of the local runs: Windows.

## 1. Database no longer replays migrations on every open

- **What it changes.** The guard of migration 018 only runs for versions below 18. It does not change the
  schema or add data.
- **Stores.** Nothing new.
- **Limits.** Versions 0.15.0 to 0.17.1 alternated the stored version (73, 57, 73, ...) on every open
  and took a backup on every other launch. Because only five backups are kept, the backup taken before an
  upgrade could be replaced by copies of itself after about ten launches. A database an old build left at
  57 is upgraded once (one backup) and then stays at the latest version. It is not known whether any user
  lost a pre-upgrade backup or a setting: in the regression test a workspace theme set to `nord` was
  reset to `midnight` by the replay.
- **If the user goes back.** The file keeps its version and the older build opens it. The older build
  then alternates the version again and takes backups again, as it always did. No data is lost by going
  back that was not already at risk.
- **Proved.** `tests/integration/db-reopen.native.test.ts` (4 tests; they fail without the fix);
  `tests/integration/upgrade-rehearsal.native.test.ts` (6 tests); `e2e/maturity-flows.ts` three real
  launches keep one version and create no `db-backups`, passing unpackaged. Not proved: the same three
  launches against the packaged binary.

## 2. Upgrade rehearsal from the previous stable release

- **What it is.** A test: the previous release's database code is read from its git tag, creates the
  database, eight tables of user data are filled, and the current code opens it.
- **Stores.** Nothing.
- **Limits.** It rehearses the database only. It does not install the previous package, run the updater
  or the installer, or use a real user profile. It needs the tag; it is skipped without it, and CI checks
  out full history. Run from `v0.17.1` again once the OxeQuery migrations 074 to 076 are merged
  (`OXESPACE_UPGRADE_FROM=v0.17.1`).
- **If the user goes back.** Not applicable.
- **Proved.** 6 tests pass in Node and in Electron, from `v0.16.0` (63 to 73).

## 3. Window hardening pinned by tests

- **What it is.** A static test over the main-process and preload sources, and a runtime check of what
  Chromium reports for every window and guest.
- **Stores.** Nothing.
- **Limits.** The static test reads source text; it makes the most dangerous edits impossible to make by
  accident and does not replace review. The runtime check covers windows, webviews and preview views that
  exist when it runs.
- **If the user goes back.** Not applicable.
- **Proved.** `tests/unit/electron-hardening.test.ts` (5 tests); `e2e/maturity-flows.ts` window and guests
  isolated, sandboxed, without Node, and `require`, `process`, `module`, `Buffer` undefined in the page,
  passing unpackaged. Not proved on the packaged binary.

## 4. Linear API key is never stored unencrypted

- **What it changes.** Without OS encryption the key is refused before it is sent or saved. It used to be
  saved in plain text while the panel said it was encrypted.
- **Stores.** The key, encrypted, in `secure_credentials` (unchanged when encryption is available).
- **Limits.** On Linux without a Secret Service (GNOME Keyring, KWallet) Linear cannot be connected until
  one is available. A key an earlier version saved unencrypted is still read, and the panel asks the user
  to reconnect.
- **If the user goes back.** A key saved encrypted by this version is read by the older one. The older
  version will again save a new key in plain text when encryption is missing.
- **Proved.** `tests/integration/linear.service.test.ts` (10 tests). Not proved on the packaged binary or
  on a Linux machine with no keychain.

## 5. RTK archive checksum

- **What it changes.** The downloaded archive is checked against the release's `checksums.txt` before it is
  extracted; a mismatch or a missing entry aborts the install.
- **Stores.** A `checksums.txt` file in the RTK folder during the download, removed afterwards.
- **Limits.** It catches truncated or swapped archives. It does not protect against a compromised release,
  where both files are controlled by the attacker; that needs a pinned hash or a signature. It fails
  closed: if the vendor stops publishing `checksums.txt`, the helper stops installing and shows an error.
  The helper is optional.
- **If the user goes back.** An already installed helper keeps working. The older version downloads without
  verification, as before.
- **Proved.** `tests/rtk-checksum.test.ts` (9 tests) and a manual check against the real v1.0.1 release (the
  genuine archive passes; the same file with one byte changed is rejected). Not proved: the download path
  inside the service (it needs Electron and the network).

## 6. Thread composer drafts survive a restart

- **Stores.** `localStorage` key `oxe.thread-drafts`: for each conversation, the unsent text and the time it
  was last edited, as plain text. At most 50 drafts of 20,000 characters; blank drafts are not stored; a
  draft not edited for seven days is deleted when drafts are next loaded or saved.
- **Limits.** Plain text on disk: a secret pasted into a message box stays there for up to seven days.
  Drafts of deleted conversations are removed by the existing catalogue reconcile.
- **If the user goes back.** Older versions ignore that key. They never purge it, so the drafts stay on
  disk, unexpired, until a version that has this feature runs again or the profile is deleted.
- **Proved.** `tests/thread-drafts.test.ts` and `tests/thread-store.test.ts` (36 tests). **Not proved in the
  packaged app, and not proved in a real window:** the composer needs an authenticated provider and the
  store is not exposed to a test. Recorded as a known limit.

## 7. First-run card "Before you start"

- **Stores.** Nothing new. It reads agent readiness and uses the existing `oxe-last-agent-health-check-at`
  key, which the agent settings already write.
- **Limits.** It checks only the agent CLIs. GitHub CLI, Git and Node cannot be checked without a workspace,
  so the card says GitHub features need `gh auth login` instead of reporting a status. The first launch runs
  one detection automatically, which starts the CLIs to read their version.
- **If the user goes back.** Nothing to undo.
- **Proved.** 17 tests (`tests/agent-setup.test.ts`, `tests/integration/FirstRunChecklist.test.tsx`); visual
  baselines, light and dark; `e2e/maturity-flows.ts` passing unpackaged with a real detection.

## 8. File trees as ARIA trees with keyboard navigation

- **Stores.** Nothing.
- **Limits.** No type-ahead, no create, rename or delete, no multi-select. In the Review tree the reviewed
  checkbox is reached with Right Arrow and a hidden description says so once. Rows are `treeitem`, not
  `button`, so automation that looked rows up as buttons must change. Not tested with a screen reader.
- **If the user goes back.** Nothing to undo.
- **Proved.** 23 component tests (`FileBrowserTree`, `ReviewFileTree`); the Changes e2e; `e2e/maturity-flows.ts` (one tab stop, Right expands and
  enters, Left returns, Enter opens a file) passing unpackaged.

## 9. Accessibility scan (axe)

- **What it is.** An informative scan, WCAG 2.0 and 2.1 A and AA, over the surfaces the visual suite
  reaches. It does not fail unless `OXE_A11Y_STRICT=1`.
- **Result and scope.** See `a11y-axe-2026-10-14.md`. A clean result says nothing about surfaces that are
  not scanned and is not a conformance claim.

## 10. Visual regression suite

- **What it is.** Screenshot comparison per platform, 42 Windows baselines.
- **Limits.** Windows only. Baselines are valid for the build they were taken on and must be regenerated at
  the release SHA. The Linux baselines come from a `workflow_dispatch` job (`e2e/visual/LINUX-BASELINES.md`).
  The first run after a rebuild failed transiently once with four failures; the cause is not known.
- **Proved.** Two consecutive full runs passed on a previous build; not yet on the release candidate.

## 11. Documentation

`docs/PRIVACY.md` and a draft `docs/COMPATIBILITY.md`. `tests/unit/docs-links.test.ts` fails when a relative
link in the README or the docs points at a missing file (plans and audits are skipped on purpose).
